The LazInk showcase

What a canvas-drawn renderer is for — written as one readable page that is also a test document.

canvas-drawn 0BSD no JavaScript no browser engine

LazInk draws formatted text on a plain TCanvas: labels, memos, list boxes, a page viewer and an editor, reading HTML or Markdown through one renderer. No WebView, no SynEdit, no GPL code — a Lazarus package that weighs what a package should. Inline it handles bold, italics, underline, strikethrough, highlighted phrases, H2O and E=mc2, links, code spans, the Ctrl+F kind of key, and the small print.

How this page is used. The demo shows it beside a browser’s picture of the same file, crosshair on, scroll-locked. Where the two sides disagree by more than a few pixels of font metric, that is a bug worth a folder in bugs/.

On this page: 1 what you could build, 2 the engine, 3 a chat window, 4 a log console, 5 tables, 6 single lines, 7 lists, 8 folds and fine print — numbered so a difference between the two halves can be named by its section, and the links jump, as they would in a help viewer.

1 · What you could build with it

Anywhere a Lazarus program shows words that deserve better than a TLabel, there is a control here for it:

A help viewer. Point TInkPage at a folder of HTML and it walks the links, finds, selects, remembers where Back goes — the manual of a real program already ships this way.
Release notes. A dialog with a page beats a memo full of asterisks: headings, links to the tracker, <details> for the long tail.
A chat window. TInkMemo appends each message as a little document on its own band — a growing answer re-lays only its own entry.
A log console. Markup per line, owner-drawn, with an in-place editor if the operator may annotate — the list box this package grew out of.
A Markdown notes app. The WYSIWYG editor reads and writes Markdown as a fixed point; nothing else for Lazarus does.
A status page. SetInnerHTML changes one element by id without rebuilding the page; the host hears clicks through OnElementClick and does what script would.

2 · The engine underneath

Since October 2026 every page stands on a real document tree: a browser’s own tag-soup parsing, the full CSS cascade, and layout from the computed styles. Flex puts cards in a row and shares the width:

Parse

Implied tags, misnested tags mended, entities, old code pages — 1706 of html5lib’s 1784 tree tests pass.

Style

Selectors with every combinator, variables, calc(), @media, light-dark() — held against getComputedStyle.

Lay out

Blocks, margins that collapse, floats, tables, flex and grid, positioning — the boxes this very page is made of.

The measure is HTML and CSS as people actually write them — an old help file, a Markdown README, a saved article should come out the way a browser draws them.

— the roadmap, on where this is going

Said plainly, not supported: JavaScript (by design, ever), words flowing line by line beside a floated picture (yet), <video>, embedded frames. The page shows its <noscript> and the fallback inside an <iframe>.
